# Design Review

화면의 목적과 제작 단계를 기준으로 관찰, 영향과 수정 방향을 연결한다. 취향을 보편적인
규칙처럼 말하지 않고, 입력 자료로 확인할 수 있는 범위를 넘겨 적합성이나 동작을 단정하지
않는다.

## 검토 범위

사용자가 달성하려는 일, 주요 사용자, 사용 맥락, 제작 단계와 적용해야 할 브랜드나
디자인 시스템을 먼저 확인한다. 정보가 부족해도 자료에서 볼 수 있는 부분은 검토하고,
결론을 바꿀 정보만 묻는다.

자료마다 확인할 수 있는 내용이 다르다.

- 스크린샷은 보이는 위계, 배치, 내용과 추정 가능한 시각 문제를 보여 준다.
- 디자인 원본은 실제 토큰·크기·컴포넌트 속성을 읽을 수 있을 때 측정 근거가 된다.
- 코드는 의미 구조, 상태, 접근 가능한 이름과 구현 관계를 보여 준다.
- 실행 화면은 키보드 조작, 포커스, 반응형 변화와 동적 상태를 시험할 수 있다.
- 보조기술 동작은 VoiceOver나 NVDA 등으로 직접 시험했을 때만 확인했다고 기록한다.

정적 자료만으로 hover, focus, 읽기 순서나 상태 전달을 통과했다고 쓰지 않는다. 정확한
값을 읽지 못한 간격과 색을 측정값처럼 만들지 않고 `추정` 또는 `미확인`으로 남긴다.

## 디자인과 사용성

현재 화면에 필요한 관점만 선택한다.

- 처음 보이는 대상과 주요 과업의 일치
- 다음 행동, 이동 경로와 결과의 예측 가능성
- 읽는 순서, 강조, 여백과 정보 밀도가 나타내는 관계
- 사용자 결정·행동·상태 이해·복구에 필요한 콘텐츠의 선택
- 제목·설명·버튼의 반복과 같은 행동 이름의 일관성
- 카드·섹션·배지·아이콘이 실제 경계나 상태를 나타내는지
- 배치의 변주, 움직임과 정보 밀도가 화면 종류·사용자·브랜드·제약과 한 방향을 이루는지
- 같은 역할의 요소와 상태가 같은 형태와 동작을 사용하는지
- 화면 크기가 달라져도 우선순위와 기능이 유지되는지
- 움직임이 조작 결과나 위계를 설명하는지, 장식적 전환이 반복되는지

생성형 화면에서 자주 보이는 표현은 개별 사용만으로 문제라고 보지 않는다. 주제와 기능에
관계없이 같은 카드, 그림자, 그라데이션, 라벨과 아이콘 조합이 반복될 때 현재 화면에서
각 요소의 역할을 확인한다.

## 접근성 감사

사용자가 접근성 감사를 요청했거나 적합성 판단이 결과의 목적일 때에는 기본적으로
[WCAG 2.2 AA](https://www.w3.org/TR/WCAG22/)를 적용한다. 다른 버전, 조직 기준이나 법적
기준이 지정되면 그 범위를 따른다. 부분 검사는 전체 준수 인증이나 법적 판단으로 표현하지
않는다.

현재 화면과 기능에 해당하는 내용을 확인한다.

- 제목, landmark, 목록, 표, 폼과 이미지 대체 텍스트의 의미 구조
- 텍스트 대비 1.4.3, 비텍스트 대비 1.4.11과 색·위치·모양에만 의존하지 않는 정보
- 200% 확대와 1.4.10 Reflow에서 내용과 기능 유지
- 모든 기능의 키보드 접근, 논리적인 순서와 보이는 포커스
- 2.4.11 Focus Not Obscured, 2.5.7 Dragging Movements의 대체 조작
- 2.5.8 Target Size (Minimum)의 24×24 CSS px 또는 간격 예외
- 입력의 영구 라벨, 자동완성 정보, 오류 위치·원인·수정 방법과 입력값 보존
- 사용자에게 보이는 라벨과 접근 가능한 이름, custom control의 role·value·state
- loading, success, error와 비동기 변경의 적절한 전달
- 시간 제한, 자동 갱신, 맥락 변화와 동작 줄이기 설정

44×44 CSS px는 유용한 설계 목표가 될 수 있지만 WCAG 2.2 AA의 일률적인 통과 기준으로
쓰지 않는다. 자동 검사만으로 감사를 끝내지 않고 가능한 범위에서 키보드, 확대·재배치와
핵심 보조기술 흐름을 직접 확인한다.

## 발견과 수정

각 발견에는 필요한 만큼 위치와 조건, 관찰 또는 측정한 증거, 영향을 받는 사용자 과업,
문제가 되는 이유, 구체적인 변경과 다시 확인할 방법을 연결한다. 접근성 발견에는 관련
성공 기준과 적합 수준을 덧붙인다.

수정 순서는 과업을 막는 정도, 대체 경로, 영향 범위와 변경 의존성으로 정한다. 근거 없는
점수, 완전성 비율과 형식적인 칭찬은 사용하지 않는다. 검토만 요청받았다면 파일을 바꾸지
않고, 수정도 요청받았다면 영향이 큰 원인을 현재 프로젝트 안에서 고친 뒤 관련 흐름을
다시 확인한다.
