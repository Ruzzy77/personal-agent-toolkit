# Corpus 작업 원칙

Corpus에서는 기능 구현보다 큰 테스트·검증·이행 구조를 만들지 않는다.

- TDD를 기본 절차로 사용하지 않는다. 필요한 동작을 가장 짧은 기존 경로에 구현한 뒤, 그 변경과 직접 관련된 확인만 한다.
- 사소한 분기나 발견한 사례마다 회귀 테스트를 추가하지 않는다. 데이터 손실, 경로 경계 또는 재현된 핵심 장애를 기존 통합 사례로 확인할 수 없을 때만 테스트를 추가한다.
- 새 테스트가 필요하면 먼저 기존 사례에 합치거나 중복 사례를 지워 테스트 총량이 늘지 않게 한다. 전용 fixture와 검증 helper는 기본적으로 만들지 않는다.
- 일상 변경에는 수정 파일의 기본 정적 검사와 직접 관련된 테스트 한두 개면 충분하다. 전체 테스트, native build, package 설치 확인은 사용자가 요청하거나 실제 release를 만들 때만 실행한다.
- 파생할 수 있는 상태를 별도 registry나 database에 저장하지 않는다. 일회성 migration, plan/apply/rollback 계층과 평가 framework를 미리 만들지 않는다.
- 같은 기능을 CLI, MCP 또는 legacy 이름으로 중복 제공하지 않는다. 기존 표면을 고치고 오래된 표면은 함께 제거한다.
- 별도 설계 문서나 작업 보고서를 기능마다 만들지 않는다. 안정된 외부 규격만 `docs/`에 두고, 사용법은 `README.md`, 제품 경계는 `DESIGN.md`에 짧게 반영한다.
- 이 plugin 폴더가 소스이자 설치 경로다. 별도 배포 사본, package builder와 생성 version 파일을 두지 않는다.
- 사용자가 승인한 Context Skill은 해당 사용자의 private Corpus 저장소에만 둔다. 개인 Skill이나 discovery bridge를 `skills/` 또는 marketplace package에 복사하지 않는다.
- 보안과 데이터 보존 검사는 실제 손실 또는 권한 침범을 막는 범위로 유지한다. 코드 모양, 미래 가능성 또는 완전성 자체를 위한 엄격한 절차는 추가하지 않는다.

변경이 이 원칙보다 큰 구조를 요구한다면 먼저 더 단순한 구현을 찾고, 그래도 필요한 경우에만 사용자에게 이유와 유지 비용을 알린다.
