# Design

사용자가 실제로 쓸 수 있는 화면을 현재 프로젝트의 기술과 디자인 언어 안에서 만든다.
정적 시안뿐 아니라 콘텐츠, 상호작용, 상태, 반응형 동작과 구현 가능한 구조를 함께 다룬다.

## 목적과 재료

누가 어떤 상황에서 무엇을 하려는 화면인지, 화면의 종류와 주요 사용자를 파악한다.
요청에 콘텐츠, 브랜드, 시각 방향과 기능이 정해져 있으면 따른다. 로고, 색, 글자와 사진
같은 기존 자산을 확인하고, 접근성·규제·신뢰처럼 잘 드러나지 않는 제약은 미적 선호보다
우선한다.

참고 화면과 디자인 파일은 방향을 이해하는 자료로 사용하되, 다른 제품의 고유한 표현을
복제하지 않는다. 정해지지 않은 세부는 주제의 실제 재료와 사용 환경에서 찾으며,
그럴듯하게 보이려고 제품 기능, 사용자 수치나 인용을 만들지 않는다.

맥락만으로 정할 수 있는 사항은 스스로 판단한다. 서로 다른 해석이 결과를 크게 바꾸고
현재 자료로 가를 수 없을 때에만 가장 결정적인 한 가지를 묻는다. 내부 계획과 자기평가를
결과보다 먼저 보여 주지 않는다.

## 선택형 참고 라이브러리

사용자가 시각 방향이나 참고 예시를 요청했거나, 현재 프로젝트만으로 구성 원리를 정하기
어려울 때에는 [선택형 디자인 참고 라이브러리](references/design-library.md)를 읽고 필요한
패턴과 레시피만 고른다. 기존 브랜드와 디자인 시스템이 충분하면 라이브러리를 불러오지
않는다. 이름이 붙은 레시피를 정답처럼 적용하거나 묶음 전체를 한꺼번에 읽지 않는다.

## 콘텐츠와 구조

대화와 자료는 화면의 재료이지 표시 의무 목록이 아니다. 사용자가 결정하고 행동하거나,
상태와 결과를 이해하거나, 오류를 복구하거나, 필요한 조건에 동의하는 데 필요한 내용만
남긴다. 논의 과정, 폐기된 대안과 구현 설명은 제품 자체에 필요하지 않다면 화면으로
옮기지 않는다.

제목, 설명과 조작 요소가 같은 내용을 되풀이하지 않게 한다. 순서, 여백, 정렬과 글자
크기로 먼저 위계를 만들고, 굵기·색·배지·아이콘·카드를 같은 의미에 겹쳐 쓰지 않는다.
카드와 섹션은 실제 경계, 상태나 하나의 조작 단위를 나타낼 때 사용한다.

## 디자인 시스템과 시각 방향

프로젝트의 토큰, 컴포넌트, 스타일, 아이콘과 레이아웃 규칙을 실제 정의와 사용처에서
확인한다. 같은 역할을 새 이름으로 다시 만들지 않고, 기존 조합으로 해결되지 않는 요구만
가장 작게 확장한다. 공개 API나 기존 사용처가 달라지는 변경에는 호환 범위와 이행 방법을
포함한다.

이름이 붙은 방향이 공식 디자인 시스템인지 시각적 경향인지 구분한다. 공식 시스템을
적용해야 한다면 실제 정의와 현재 프로젝트의 사용 버전을 확인한다. 편집적 구성,
타일형 배치나 반투명 표면 같은 미적 방향을 공식 시스템처럼 다루지 않는다.

색, 글자, 배치, 이미지와 움직임이 하나의 방향을 만들게 한다. 배치의 규칙성과 변주,
움직임의 정도, 화면당 정보 밀도를 고정 점수나 용도별 기본값으로 정하지 않고 화면 종류,
사용자, 브랜드, 콘텐츠 양과 제약에서 판단한다.

글자는 화면의 성격과 정보 위계를 함께 만든다. 본문은 현재 언어와 글꼴에서 편하게 읽을
수 있는 줄 길이와 간격을 사용한다. 한 글꼴의 굵기와 너비만으로 역할을 나눌 수 있으며,
여러 글꼴을 쓴다면 차이와 역할이 분명해야 한다. 번호, 구분선, 라벨과 눈썹 제목은 실제
순서나 구분을 나타낼 때만 사용한다.

유행하는 카드, 그림자, 그라데이션, 대문자 라벨, 고정폭 글꼴이나 화살표를 개별 금지
항목으로 판정하지 않는다. 이런 표현이 내용과 브랜드에 관계없이 한 묶음으로 반복되면
각각 맡는 역할을 다시 확인하고 근거가 없는 요소만 덜어낸다.

## 새 화면과 개편

새 화면인지, 현재 모습을 유지하며 다듬는 개편인지, 구조나 시각 방향을 다시 만드는
작업인지 구분한다. 개편에서는 현재 토큰과 브랜드 자산, 콘텐츠와 정보 구조, 주요 흐름과
상태, 반응형 동작, 접근성, 폼과 추적에 쓰이는 이름을 먼저 확인해 유지할 것과 바꿀 것을
나눈다.

변경 범위에 포함되지 않은 URL, 주요 탐색 이름, 폼 필드의 이름과 순서, 로고·워드마크,
법적 고지와 동의 문구를 조용히 바꾸지 않는다. 전면 재작성보다 원인이 큰 문제를 작은
변경으로 먼저 해결하고, 기존 구조가 실제 과업을 감당하지 못할 때에만 교체한다.

방향을 탐색하는 단계에서는 내용 관계와 주요 흐름을 확인할 수 있는 와이어프레임이나
작동하는 프로토타입부터 만들 수 있다. 여러 안은 실제 선택에 필요한 차이가 있을 때만
소수로 제시한다. 방향이 정해지면 관련 컴포넌트, 스타일과 문구를 국소적으로 편집한다.

## 상호작용, 문구와 접근성

기본 상태뿐 아니라 필요한 hover, focus, active, selected, disabled, loading, empty와
error 상태를 다룬다. 사용자의 조작에 응답하는 움직임은 무엇이 바뀌었는지 보여 주게
한다. 자동으로 시작하는 움직임은 시선을 모아야 할 지점에 제한하고 동작 줄이기 설정을
존중한다.

화면 문구는 사용자가 알아보는 대상과 행동을 직접 말한다. 같은 대상과 행동에는 같은
이름을 쓰며, 버튼에는 실행 뒤 일어나는 결과를 드러낸다. 오류와 빈 화면에는 확인된
원인과 실제로 가능한 다음 행동을 쓴다. 삭제·권한 변경처럼 되돌리기 어려운 작업에는
대상, 범위와 결과를 모호하게 줄이지 않는다.

의미 구조, 키보드 조작, 보이는 포커스, 대비, 확대와 재배치, 접근 가능한 이름과 상태
전달을 구현의 일부로 다룬다. 별도의 적합성 감사가 필요하면 `design-review`의 접근성
감사 범위를 적용한다.

## 구현과 개발 인계

프로젝트의 프레임워크, 의존성, 파일 구조와 스타일 방식을 확인한 뒤 그 안에서 구현한다.
시각적 이유만으로 기술 스택을 바꾸거나 의미 있는 구조와 동작을 없애지 않는다. 새
의존성을 쓰기 전에 현재 프로젝트에 있는지 확인하고, 필요한 이유 없이 추가하지 않는다.

개발 인계를 요청받으면 원자료에서 확인되는 범위로 화면 목적, 레이아웃, 토큰,
컴포넌트와 상태, 반응형 변화, 콘텐츠 제약, 자산, 움직임과 접근성 동작을 정리한다.
확인한 값, 화면에서 추정한 관계와 아직 정하지 않은 사항을 구분하고, 존재하지 않는
breakpoint, prop이나 애니메이션 값을 정밀한 사양처럼 만들지 않는다. 완료 조건은 문서
항목 수가 아니라 주요 사용자 흐름과 대표 상태를 재현할 수 있는지로 쓴다.

## 실제 화면으로 확인

가능하면 화면을 실행하거나 렌더링해 대표적인 큰 화면과 작은 화면에서 확인한다. 내용의
겹침·잘림, 읽기 어려운 대비, 불분명한 위계, 보이지 않는 키보드 포커스, 불안정한
반응형 전환, 누락된 상태와 과한 움직임을 고친다. 확인하지 않은 화면과 동작을 완료된
결과로 보고하지 않는다.
