# Journal 설계

## 목적과 경계

Journal은 현재 주의 간결한 진행 상태, 사용자가 확정한 해결 상태와 마감된 기간 기록을 관리한다.
원문 이메일·문서를 복제하지 않고 필요한 요약과 source reference만 저장한다. 프로젝트의 오래가는
사실과 결정은 Journal에 쌓지 않고 확인된 결과만 해당 Corpus Context로 반영한다.

## 구성과 실행

- `plugins/journal`: Skill, 클라이언트별 원격 연결과 제한된 로컬 모니터 launcher
- `services/journal`: 인증, MCP·HTTP API, 업무 규칙과 D1 저장
- `sites/journal`: 같은 service API를 사용하는 소유자 전용 UI

service가 유일한 데이터 권위다. Site는 자체 D1·R2를 갖지 않는다. launcher는 원격 MCP를 사용할
수 없는 모니터의 읽기·ingest 보조 수단이며 별도 정본을 만들지 않는다.

## 데이터와 변경

Journal D1은 현재 항목, append-only event, 확정된 주간 마감과 정정을 보관한다. 자동 ingest는
관찰된 진행을 갱신할 수 있지만 완료·보류·취소·재개를 추론하지 않는다. 마감 뒤 변경은 기존 기록을
덮지 않고 correction으로 남긴다.

## 공개 표면과 권한

MCP와 HTTP는 같은 service 함수를 호출한다. 공개 도구 목록과 version은 루트
[`products.json`](../../products.json)이 정본이다. owner OAuth scope는 읽기, ingest와 쓰기를
구분하고 Site-to-service token 및 모니터 token은 서로 다른 실행 경계에서 사용한다.

저장되지 않은 주의 보드와 마감 준비는 `status=open`, `revision=0`인 가상 주를 반환하며
읽기만으로 주를 저장하지 않는다. 두 읽기 출력은 이 가상 주와 저장된 주를 구분해 허용한다.
실제 마감 결과와 기간에 포함되는 저장된 주의 revision은 1 이상이어야 한다.

## 버전과 검증

plugin, service와 Site는 같은 제품 release version을 사용한다. 상태 전이, 주간 마감, 권한과 D1
migration을 집중 검증하고 단순 화면 문구나 상수 복제에는 회귀 테스트를 늘리지 않는다. 배포 완료는
service와 Site가 시작되고 새 클라이언트 세션에서 현재 MCP 표면이 확인된 상태다.

## 현재 주 자동 연속성 — 2026-09-09

현재 주의 열린 보드는 해당 주의 기록과 이전 모든 주의 최신 `active`·`held` 인스턴스를 합쳐 읽는다. 같은 출처의 후속 완료·취소가 있으면 과거 미완료를 다시 표시하지 않는다. 과거 주 조회는 그 주에 저장된 인스턴스와 사건을 그대로 반환한다. 현재 주 검색·주간 집계도 같은 투영을 사용한다.

읽기는 주나 항목을 생성하지 않는다. 이전 항목에 새 관찰이나 사용자 상태 변경을 저장할 때만 현재 주 인스턴스와 이월·변경 사건을 원자적으로 생성한다. 원본 version과 후속 인스턴스 부재를 저장 조건으로 확인하며 과거 항목은 보존한다. 상태 변경 재시도는 새 인스턴스를 반환한다. `held`와 대기 담당을 유지하며 확정 결과와 Corpus 후보를 자동 복사하지 않는다.

Site는 미완료를 한 보드에서 모두 표시하고 별도 이전 주 목록·일상 마감 버튼을 없앤다. 과거 주가 열려 있어도 마감을 요구하지 않는다. 기존 명시적 기록 동결 API는 호환 유지하며, 아래 Corpus 영수증의 동결 후 처리 정책은 별도 미구현 범위다. 이번 변경은 그 정책이나 운영 주의 마감을 실행하지 않는다.

## 개선 검토와 다음 범위

2026-09-05의 첫 조사에서는 기록 수집, 사용자 처리 상태와 기간 기록을 분리한 기본 구조를
유지한다. 현재 주의 실제 사용은 확인했지만, 보류·주간 마감 때문에 발생한 관리 부담의 크기는
확인하지 않았다. 다음 범위는 기능 확대보다 실패 복구와 업무의 주간 연속성에 둔다.

1. **Corpus 반영 실패 후 복구:** 기존 service와 저장층이 실패 기록까지 중복으로 판단해 이후
   적용·건너뛰기를 받지 않는 문제를 격리 환경에서 재현했다. 아래와 같이 실패 이력을 보존하고
   완료만 한 건으로 제한하는 수정을 구현했다. 운영에서 실제 실패가 발생했는지는 확인하지 않았다.
2. **보류·미마감 업무의 연속성:** 현행 계약은 보류 항목을 주간 마감 때 다음 주의 진행 중 항목으로
   만든다. 기본 보드에는 마감하지 않은 지난주의 미해결 항목이 자동으로 포함되지 않는다.
   사용자는 아래와 같이 보류 유지 정책을 채택했으며, 필요한 이월·조회 변경은 후속 구현으로 남아 있다.

2026-09-06에는 운영 중인 주의 보드와 마감 준비를 읽기만 했다. 이월 후보에 보류 항목이 없었고
Corpus 반영 후보에는 모두 처리 기록이 있어, 이번 사례에서는 보류 상태 전환의 부담이나 미반영으로
인한 마감 지연을 확인하지 못했다. 처리 기록 조회를 대상 Corpus 본문의 현재성 확인으로 해석하지
않는다. 이 검토를 위해 항목 상태를 바꾸거나 주를 마감하지 않았다. 이후 사용자가 다음 두 정책을
채택했으며, 앞선 사례를 정책 변경의 효과가 입증된 결과로 해석하지 않는다.

### 이전 채택 정책 — Corpus 마감 조건은 구현 대기, 보류 유지는 반영

- **Corpus 반영 전 마감 허용:** 반영 후보에 미처리 건이 있어도 주간 마감을 허용한다. 마감 과정에서
  Journal의 확정 결과와 해당 Corpus 내용을 대조하고, 확인된 불일치는 적절한 정본에 반영하거나
  개정한다. 미처리·실패를 자동으로 `applied`나 `skipped`로 바꾸지 않으며, 처리하지 못한 건은
  마감 뒤에도 식별하고 이어서 처리할 수 있어야 한다. Journal의 마감 기록을 고쳐야 할 때에는
  기존 기록을 덮지 않고 correction을 남긴다.
- **보류 상태 유지:** 보류 항목은 다음 주에도 `held`로 이월하며, 사용자가 재개를 확인하기 전까지
  진행 중으로 바꾸지 않는다. 이미 다음 주에 같은 업무가 있으면 그곳의 사용자 확정 상태를
  덮어쓰지 않는다. 과거 이월 기록에서 현재 상태를 추정해 일괄 복원하지 않는다.

현행 구현은 미반영 후보가 있으면 마감을 거절하고, 마감된 주의 새 반영 영수증도 거절한다.
보류 유지와 미완료 조회는 위 2026-09-09 변경으로 반영했다. 따라서 정책 채택을 구현·운영 반영의
완료로 보고하지 않는다. 후속 범위는 service·저장층의 마감 조건과 마감 후 반영 기록, 보류 이월,
Site·Skill의 마감 안내를 함께 맞추는 것이다. 마감된 후보와 후속 정정의 대응, 실패 이력·멱등성·
중복 완료 보호, 준비 이후 변경의 충돌 검사를 보존하는 세부계획과 필요한 확인·배포·복구 범위를
정한 뒤 구현한다. 다른 독립 개선이나 실제 문서 작업의 선행 조건으로 삼지 않으며, 이번 정책
기록만으로 운영 항목·주간 마감·Corpus 내용을 변경하지 않는다.

수집은 안정된 출처 키와 변경별 멱등 키를 사용하는 현행 계약을 유지한다. 같은 관찰의 반복 수집이나
서로 다른 출처가 같은 업무를 중복 생성하는 문제가 실제 확인될 때만 해당 경로를 보강한다.

### Corpus 반영 실패의 재시도

주간 마감·보류 정책의 선택과 독립된 변경이다. **실패 영수증을 덮어쓰지 않고
시도별 행을 추가하며, 같은 후보의 완료(`applied` 또는 `skipped`)만 한 건으로 제한**하는 방식을
채택한다. 기존 행을 갱신하려면 사건에 없는 과거 실패 details까지 별도로 보존해야 하므로,
현재 영수증·사건을 그대로 유지한다. 소스 구현·격리 확인과 운영 이관·서비스 반영을 마쳤다.
일부 클라이언트의 갱신·실제 읽기 확인은 아래와 같이 남아 있다.

- **저장과 이관:** 새 migration에서 영수증 테이블의 후보 전체 UNIQUE를 완료 상태의 partial
  unique로 바꾼다. `item_id`가 있는 후보와 NULL인 후보의 인덱스를 구분하며 기존 ID·상태·경로·
  details·기록 시각과 사건은 그대로 보존한다. 이관 전 완료 중복을 검사하고 발견하면 임의 정리
  없이 중단한다. 이번 복구 스냅샷은 applied 3건, NULL 후보와 완료 중복은 없었으며 이 수치를
  실제 이관 전 재조회 대신 사용하지 않는다.
- **재전송과 새 시도:** 같은 `idempotencyKey`는 새 행·사건을 만들지 않는다. 실패 뒤 다른 시도는
  새 키를 사용한다. 이미 완료된 후보에는 추가 완료나 실패를 기록하지 않고 기존 완료를 중복으로
  반환한다. 새 사건에는 `receiptId`와 `details`를 남기되 과거 사건의 관계를 추정해 채우지 않는다.
  같은 키에서 저장된 후보·상태·경로가 바뀌면 충돌로 거부한다. `details` 대조는 이를 저장한 새
  사건에 적용하며, 해당 값이 없는 과거 사건은 details만 달라져도 중복으로 반환하고 이력을 바꾸지 않는다.
- **저장 시점의 보호:** 열린 주, 읽었던 항목 version과 완료 영수증 부재를 삽입 조건으로 검사한다.
  영수증과 사건은 같은 D1 batch에 넣고 실제 삽입된 영수증에만 사건을 연결한다. 삽입이 없으면
  기존 키·완료 여부를 다시 읽어 중복과 충돌을 구분하며 다른 DB 오류를 성공으로 처리하지 않는다.
- **확인과 반영:** 기존 검사와 일회성 확인으로 반복 실패 뒤 완료, 같은 키 재전송, 완료 경쟁,
  NULL 후보, 사건 실패의 전체 롤백, 항목 변경·마감과의 충돌 및 기존 행 보존을 확인한다. 실패만
  있으면 마감을 막고 완료가 추가되면 허용하는 당시 정책을 유지했다. 이 조건은 위 채택 정책의
  후속 구현에서 변경할 대상이다. service·영수증 기록 Skill·운영
  안내를 함께 맞추고, 백업과 격리 복구를 확인한 release에서 개별·통합 Worker를 함께 반영한다.
  구형 Worker로 돌아가면 실패가 다시 재시도를 막으므로 schema를 되감거나 복구 완료로 간주하지 않는다.

기존 Journal 23개·통합 서비스 20개·Site 3개 검사와 일회성 API·경쟁 검사 11개를 통과했다.
새 운영 export를 격리 D1에 복원한 뒤 `0006_promotion_attempts.sql`을 적용해 기존 8개 테이블의
모든 행 값, FK와 무결성이 유지됨을 확인했다. 별도의 가상 NULL 완료 중복은 원본 행을 보존하며
복사·삭제 전에 중단했다. 이 격리 확인은 운영 migration이나 실제 Corpus 쓰기의 성공을 뜻하지 않는다.

소스 `6783ea8`의 원격 검사를 통과한 뒤 Journal 0.2.3의 운영 migration과 개별·통합 Worker,
비공개 Site 9를 함께 반영했다. 이관 직전·직후 export를 대조해 기존 업무·사건·영수증·수집·기간
기록의 모든 행 값이 유지되고 migration 장부에 0006 한 행만 추가됐음을 확인했다. 무결성·FK와
완료 인덱스 두 개도 정상이었으며 대기 migration은 없다. 확인용 운영 쓰기는 실행하지 않았다.

Codex 통합 plugin과 Claude Code의 Journal을 정상 갱신해 현재 Skill의 소스 일치를 확인했다.
새 비지속 Codex 세션에서 두 재시도 지침과 당시 주의 항목 21개를 실제로 읽었다. 이후 플랫폼별
갱신 결과와 남은 확인은 Corpus `personal-agent-toolkit` Space의 `design` 문서에 있는
05 진행 상태에서 관리한다.
클라이언트의 실제 도구 설명·읽기 확인을 서비스 반영이나 설치 성공으로 대신하지 않는다.

이 변경이 보호하는 범위는 **영수증 저장의 중복과 경쟁**이다. 현행 Skill은 Corpus에 실제로 반영한
뒤 영수증을 남기므로 외부 Corpus 쓰기 자체의 동시 실행까지 막는다고 하지 않는다. 별도 선점·잠금
계약은 추가하지 않는다.

### 마감 준비와 저장의 항목 일치

격리 D1에서 확정 요청의 준비 조회와 후속 항목 재조회 사이에 결과·처리 상태·항목 수를 각각
바꾸자, 세 경우 모두 이전 요약·후보로 마감됐다. 저장 시점의 version 검사가 두 번째 조회 값을
받아 변경을 놓친 것이며, 운영 기록에서 같은 문제가 발생했는지는 확인하지 않았다.

마감 준비의 요약·후보·이월과 저장 사전조건을 **한 번 읽은 동일한 항목 목록**에서 만든다.
공개 준비 응답은 그대로 두고 내부 준비 함수만 항목 목록을 함께 반환하며, 확정 중 항목 재조회를
없앤다. 준비 이후 변경은 기존 D1 batch의 항목 수·version 검사로 거절하고 마감·이월 사건을
남기지 않는다. 최신 변경은 보존하며, 다시 준비한 뒤 필요한 영수증을 갖춰 확정할 수 있어야 한다.
주간 마감·보류·Corpus 반영 정책과 공개 MCP 입력, 저장 schema는 바꾸지 않는다.

같은 경합 세 가지와 재준비·정상 마감, 기존 Journal·통합 서비스·Site 검사를 확인한 뒤 개별·통합
Worker의 같은 구현을 함께 반영한다. 공개 Skill·입력 변경이 없다면 설치·인증을 반복하지 않는다.

구현 뒤 세 경합 모두 마감·이월 없이 거절됐고 최신 변경은 남았다. 새 결과의 영수증이 없으면
재준비 후에도 마감을 막으며, 필요한 영수증을 갖춘 뒤 현재 요약으로 마감·이월하고 같은 요청은
사건 추가 없이 반환했다. 기존 Journal 23개와 일회성 경합 검사 3개, 통합 서비스 20개 및 Site
3개 검사를 통과했다. 일회성 검사 파일은 확인 후 정리했다. 공개 준비 응답과 Skill·입력·저장
schema는 그대로이므로 Journal 0.2.3의 호환 가능한 서버 내부 수정으로 다뤘다. 후속 운영 번들
대조에서 통합 Worker의 구형 의존성 복사본을 확인했으므로, 개별 Worker의 반영을 통합 반영으로
확대하지 않는다. 정정 배포와 확인 범위는 루트 설계에서 관리한다. Site는 같은 API를 중계하므로
소스·배포를 다시 만들지 않는다.

### 기록 없는 주의 읽기

실제 모니터링의 지난주 보드 조회에서 revision 하한의 출력 검증 오류가 발생했다. 격리 D1의
HTTP 응답에서 열린 가상 주의 revision 0을 직접 확인했고, 개별·통합 MCP의 보드와 마감 준비
네 호출에서 같은 오류를 재현했다. 서비스의 읽기 동작은 유지하고 위 두 출력의 검증만 맞췄다.

수정 뒤 없는 주와 저장된 빈 주의 두 MCP 읽기가 통과했으며 조회 전후 모든 테이블의 행이
유지됐다. 음수·소수·마감된 주의 0과 실제 마감 결과·기간의 0은 계속 거부한다. 기존 Journal
23개·통합 20개와 일회성 5개 확인 및 양쪽 typecheck를 통과했고 임시 검사는 정리했다.
Journal 0.2.4 반영 묶음은 이 출력 정정과 모니터링 안내를 포함하며 저장 이관·운영 자료 정비나
주간 정책 변경은 포함하지 않는다.
