# Journal 설계

## 목적과 경계

Journal은 현재 주의 간결한 진행 상태, 사용자가 확정한 해결 상태와 마감된 기간 기록을 관리한다.
원문 이메일·문서를 복제하지 않고 필요한 요약과 source reference만 저장한다. 프로젝트의 오래가는
사실과 결정은 Journal에 쌓지 않고 확인된 결과만 해당 Corpus Context로 반영한다.

## 구성과 실행

- `plugins/journal`: Skill, 클라이언트별 원격 연결과 제한된 로컬 모니터 launcher
- `services/journal`: 인증, MCP·HTTP API, 업무 규칙과 D1 저장
- `sites/journal`: 같은 service API를 사용하는 소유자 전용 UI

service가 유일한 데이터 권위다. Site는 자체 D1·R2를 갖지 않는다. launcher는 원격 MCP를 사용할
수 없는 모니터의 읽기·ingest 보조 수단이며 별도 정본을 만들지 않는다.

## 데이터와 변경

Journal D1은 현재 항목, append-only event, 확정된 주간 마감과 정정을 보관한다. 자동 ingest는
관찰된 진행을 갱신할 수 있지만 완료·보류·취소·재개를 추론하지 않는다. 마감 뒤 변경은 기존 기록을
덮지 않고 correction으로 남긴다.

## 공개 표면과 권한

MCP와 HTTP는 같은 service 함수를 호출한다. 공개 도구 목록과 version은 루트
[`products.json`](../../products.json)이 정본이다. owner OAuth scope는 읽기, ingest와 쓰기를
구분하고 Site-to-service token 및 모니터 token은 서로 다른 실행 경계에서 사용한다.

## 버전과 검증

plugin, service와 Site는 같은 제품 release version을 사용한다. 상태 전이, 주간 마감, 권한과 D1
migration을 집중 검증하고 단순 화면 문구나 상수 복제에는 회귀 테스트를 늘리지 않는다. 배포 완료는
service와 Site가 시작되고 새 클라이언트 세션에서 현재 MCP 표면이 확인된 상태다.

## 개선 검토와 다음 범위

2026-09-05의 첫 조사에서는 기록 수집, 사용자 처리 상태와 기간 기록을 분리한 기본 구조를
유지한다. 현재 주의 실제 사용은 확인했지만, 보류·주간 마감 때문에 발생한 관리 부담의 크기는
확인하지 않았다. 다음 범위는 기능 확대보다 실패 복구와 업무의 주간 연속성에 둔다.

1. **Corpus 반영 실패 후 복구:** 기존 service와 저장층이 실패 기록까지 중복으로 판단해 이후
   적용·건너뛰기를 받지 않는 문제를 격리 환경에서 재현했다. 아래와 같이 실패 이력을 보존하고
   완료만 한 건으로 제한하는 수정을 구현했다. 운영에서 실제 실패가 발생했는지는 확인하지 않았다.
2. **보류·미마감 업무의 연속성:** 현행 계약은 보류 항목을 주간 마감 때 다음 주의 진행 중 항목으로
   만든다. 기본 보드에는 마감하지 않은 지난주의 미해결 항목이 자동으로 포함되지 않는다.
   보류의 의미를 먼저 정한 뒤 필요한 이월·조회 변경만 계획한다.

주간 마감과 Corpus 반영을 분리하고, 보류는 명시적 재개까지 유지하는 방향을 권고한다. 두 변경은
아직 사용자 선택 전이며 현행 계약에 반영하지 않았다. 선택 뒤 service·Site·Skill의 세부계획과
기존 기록의 취급, 필요한 검사·배포·복구 범위를 함께 정한다. 조사 중 운영 항목의 상태나 마감을
바꾸지 않으며, 제품 개선을 실제 Corpus 반영의 승인으로 대신하지 않는다.

수집은 안정된 출처 키와 변경별 멱등 키를 사용하는 현행 계약을 유지한다. 같은 관찰의 반복 수집이나
서로 다른 출처가 같은 업무를 중복 생성하는 문제가 실제 확인될 때만 해당 경로를 보강한다.

### Corpus 반영 실패의 재시도

주간 마감·보류 정책의 선택과 독립된 변경이다. **실패 영수증을 덮어쓰지 않고
시도별 행을 추가하며, 같은 후보의 완료(`applied` 또는 `skipped`)만 한 건으로 제한**하는 방식을
채택한다. 기존 행을 갱신하려면 사건에 없는 과거 실패 details까지 별도로 보존해야 하므로,
현재 영수증·사건을 그대로 유지한다. 소스 구현과 격리 확인을 마쳤으며 운영 이관·배포는 대기 중이다.

- **저장과 이관:** 새 migration에서 영수증 테이블의 후보 전체 UNIQUE를 완료 상태의 partial
  unique로 바꾼다. `item_id`가 있는 후보와 NULL인 후보의 인덱스를 구분하며 기존 ID·상태·경로·
  details·기록 시각과 사건은 그대로 보존한다. 이관 전 완료 중복을 검사하고 발견하면 임의 정리
  없이 중단한다. 이번 복구 스냅샷은 applied 3건, NULL 후보와 완료 중복은 없었으며 이 수치를
  실제 이관 전 재조회 대신 사용하지 않는다.
- **재전송과 새 시도:** 같은 `idempotencyKey`는 새 행·사건을 만들지 않는다. 실패 뒤 다른 시도는
  새 키를 사용한다. 이미 완료된 후보에는 추가 완료나 실패를 기록하지 않고 기존 완료를 중복으로
  반환한다. 새 사건에는 `receiptId`와 `details`를 남기되 과거 사건의 관계를 추정해 채우지 않는다.
  같은 키에서 저장된 후보·상태·경로가 바뀌면 충돌로 거부한다. `details` 대조는 이를 저장한 새
  사건에 적용하며, 해당 값이 없는 과거 사건은 details만 달라져도 중복으로 반환하고 이력을 바꾸지 않는다.
- **저장 시점의 보호:** 열린 주, 읽었던 항목 version과 완료 영수증 부재를 삽입 조건으로 검사한다.
  영수증과 사건은 같은 D1 batch에 넣고 실제 삽입된 영수증에만 사건을 연결한다. 삽입이 없으면
  기존 키·완료 여부를 다시 읽어 중복과 충돌을 구분하며 다른 DB 오류를 성공으로 처리하지 않는다.
- **확인과 반영:** 기존 검사와 일회성 확인으로 반복 실패 뒤 완료, 같은 키 재전송, 완료 경쟁,
  NULL 후보, 사건 실패의 전체 롤백, 항목 변경·마감과의 충돌 및 기존 행 보존을 확인한다. 실패만
  있으면 마감을 막고 완료가 추가되면 허용하는 정책은 유지한다. service·영수증 기록 Skill·운영
  안내를 함께 맞추고, 백업과 격리 복구를 확인한 release에서 개별·통합 Worker를 함께 반영한다.
  구형 Worker로 돌아가면 실패가 다시 재시도를 막으므로 schema를 되감거나 복구 완료로 간주하지 않는다.

기존 Journal 23개·통합 서비스 20개·Site 3개 검사와 일회성 API·경쟁 검사 11개를 통과했다.
새 운영 export를 격리 D1에 복원한 뒤 `0006_promotion_attempts.sql`을 적용해 기존 8개 테이블의
모든 행 값, FK와 무결성이 유지됨을 확인했다. 별도의 가상 NULL 완료 중복은 원본 행을 보존하며
복사·삭제 전에 중단했다. 이 격리 확인은 운영 migration이나 실제 Corpus 쓰기의 성공을 뜻하지 않는다.

이 변경이 보호하는 범위는 **영수증 저장의 중복과 경쟁**이다. 현행 Skill은 Corpus에 실제로 반영한
뒤 영수증을 남기므로 외부 Corpus 쓰기 자체의 동시 실행까지 막는다고 하지 않는다. 별도 선점·잠금
계약은 추가하지 않는다. 마감 준비 검증 뒤 항목을 다시 읽는 경로에서 후보가 바뀔 가능성도 코드상
별도 쟁점으로 남아 있으며, 실제 재현 없이 이 재시도 수정의 해결 범위에 포함하지 않는다.
